# seoul_rent_api

seoul_rent_data analysis

## 서울시 전월세 가격 분석

서울시 전월세 실거래 자료를 바탕으로 2021~2025년 가격 변화를 분석하고,
분석 결과를 공개하는 프로젝트입니다.

## 분석 범위와 기준

- 기간: 계약일 기준 2021년 1월~2025년 12월
- 지역: 서울시 전체; 자치구별 결과도 산출할 수 있도록 자치구를 보존
- 대상: 전세 및 월세 계약
- 기본 가격 지표: 계약별 전세환산 보증금의 월별 중앙값
- 거래량 지표: 월별 유효 계약 건수
- 기간 비교: 연도별 중앙값 및 전년 대비 변화율
- 금액 표시: API 원자료의 단위를 확인한 뒤 일관된 단위로 정규화
- 가격 기준: CPI 보정 없이 명목가격만 분석

월세 계약은 아래 고정 전환율 5.0%를 사용해 전세환산 보증금을 계산합니다.
전세 계약은 월세가 0원이므로 기존 보증금이 그대로 지표에 반영됩니다.

```text
전세환산 보증금 = 보증금 + (월세 × 12 ÷ 0.05)
```

전환율은 기준 시나리오로 고정하며, 결과물에는 5.0%를 사용했다는 점을
명시합니다. 이 값은 분석상 가정이며 실제 계약의 경제적 가치와 같다고
해석하지 않습니다.

현재 분석에서는 CPI 보정지표를 제외합니다. 따라서 가격 변화는 물가를 조정하지
않은 명목가격 기준으로 해석합니다.

## 데이터 및 비밀정보

API 키는 로컬 `.env` 파일의 `SEOUL_OPEN_DATA_API_KEY` 환경 변수로 관리합니다.
`.env`는 Git에 추가하지 마세요. `.env.example`에는 변수명만 두고 실제 키를
입력하지 않습니다. 자동 실행 시에는 GitHub Actions secret으로 키를 전달하고,
배포되는 브라우저 코드나 공개 파일에 키를 포함하지 않습니다.

원본 API 응답은 `data/raw/`에 보관하며 Git에는 올리지 않습니다.
공개에 필요한 가공 결과만 별도로 생성합니다.
표준화한 전체 원자료도 용량이 크므로 `data/processed/*.csv.gz`로 생성하고
Git에는 추가하지 않습니다.

## 공통 스키마로 정규화

첨부된 API 명세의 23개 필드명을 표준 열 이름으로 사용합니다. CSV 한글 열과
API JSON 필드를 같은 열로 변환하고, 모든 원본 파일을 하나의 gzip CSV로
결합합니다. 원본은 수정하지 않으며 각 행에 `SOURCE_FILE`, `SOURCE_ROW`를
추가해 출처를 추적합니다. 이 단계에서는 중복을 제거하지 않습니다.

- 계약일 `CTRT_DAY`: `YYYYMMDD` 형식
- 금액 `GRFE`, `RTFE`, `BFR_GRFE`, `BFR_RTFE`: 만원 단위 유지
- 면적 및 수치 필드: 십진수 정규화
- 지번 코드(`MNO`, `SNO`) 및 행정구역 코드: 문자열로 보존하여 앞자리 0 유지
- 접수연도 `RCPT_YR`와 계약일 `CTRT_DAY`: 서로 구분해 보존

```sh
python3 scripts/normalize_data.py
```

기본 출력은 `data/processed/seoul_rent_standardized.csv.gz`입니다. 출력이 이미
있으면 덮어쓰지 않습니다. 변환이 실패하면 `.part` 파일이 남으므로 오류를
확인한 뒤 해당 임시 파일을 처리하고 재실행합니다.

2026년 10월 10일 현재 6개 원본 파일의 총 4,281,097행을 표준화했습니다.
결과는 25열(명세 23열 + 출처 2열), gzip CSV 약 111 MB이며 계약일 형식
검사에서 잘못된 날짜는 없었습니다. 원본 파일별 행 수와 변환 결과의 출처별
행 수가 일치하는 것도 확인했습니다. 파일 간 중복 제거는 하지 않았습니다.

## API 사전 점검

자료: [서울시 부동산 전월세 실거래가 정보 (OA-21276)](https://data.seoul.go.kr/dataList/OA-21276/S/1/datasetView.do)

공식 샘플 응답에서 확인한 OpenAPI 서비스명은 `tbLnOpendataRentV`입니다.
응답에는 `CTRT_DAY`(계약일), `RENT_SE`(전월세 구분), `GRFE`(보증금),
`RTFE`(월세), `CGG_NM`(자치구명) 등이 포함됩니다. 분석 기간은 `RCPT_YR`
(접수연도)가 아니라 `CTRT_DAY`(계약일)로 필터링합니다.

포털은 OpenAPI가 최근 3년 데이터부터 제공된다고 안내합니다. 현재는 2021~2023년
포털 연도별 파일과 2024~2026 접수연도 API 자료를 확보했습니다. 2021~2025년
분석 행은 `CTRT_DAY` 계약일로 선택합니다. 접수연도와 계약연도는 다를 수 있고
인접 연도 행도 파일에 포함되므로, 출처 간 중복 후보를 별도로 점검합니다.

API 키는 개인 키로 발급받아 사용하세요. 확인된 엔드포인트는 HTTP이므로
키가 네트워크 전송 중 암호화되지 않습니다. 키를 저장소, 브라우저, 로그,
배포 환경에 넣지 말고, 신뢰할 수 있는 네트워크에서 로컬 점검·수집에만
사용하세요.

```sh
cp .env.example .env
# .env를 편집해 SEOUL_OPEN_DATA_API_KEY에 발급받은 키를 입력합니다.
set -a
. ./.env
set +a
python3 scripts/inspect_api.py
```

점검 스크립트는 첫 5개 행의 스키마와 요약만 출력하며 API 키나 원자료 행을
출력하지 않습니다. 성공 확인 전에는 전체 수집을 실행하지 않습니다.

## API 수집기

`scripts/fetch_api.py`는 접수연도 2026, 2025, 2024를 각각 API에 지정해
페이지당 최대 1,000행씩 전체 수집합니다. 실행하면 연도별로 아래 파일을
`data/raw/`에 생성하며, 응답의 모든 행을 보존합니다. 계약연도로는 여기서
필터하지 않습니다.

```text
data/raw/api_receipt_2026.jsonl
data/raw/api_receipt_2025.jsonl
data/raw/api_receipt_2024.jsonl
```

공식 URL 인자 순서는 `/{KEY}/json/tbLnOpendataRentV/{START}/{END}/{RCPT_YR}/`
입니다. 서비스 필터는 인자 이름/값 쌍이 아니라 값만 순서대로 덧붙입니다.
따라서 `.../1/1000/2025/`가 2025 접수연도의 첫 페이지 요청입니다.

실제 키로 검증한 총 건수는 2024년 1,114,387건, 2025년 1,085,051건,
2026년 450,506건입니다. 수집기는 페이지마다 접수연도를 검증하고, 50페이지마다
진행 상황을 출력합니다. 모든 페이지를 받으면 `.part` 임시 파일을 연도별 JSONL로
확정합니다. 네트워크 오류나 중단 시 부분 파일은 `.part`로 남으며, 완성 파일은
덮어쓰지 않습니다. 부분 파일을 재실행할 때는 처음부터 다시 받습니다.

2026년 10월 10일 전체 수집 결과, 세 API 파일의 저장 행 수는 각각
2024년 1,114,387건, 2025년 1,085,051건, 2026년 450,506건으로 API의 전체 건수와
일치했습니다. 2023 포털 파일까지 받은 뒤 원본 행을 `CTRT_DAY` 계약연도로 세면
2021년 464,824건, 2022년 576,508건, 2023년 584,290건, 2024년 1,121,835건,
2025년 1,041,568건입니다. 이 합계는 파일 간 중복 제거 전 원자료 행 수입니다.

접수연도와 계약연도는 서로 다른 기준이므로 연도별 건수는 같지 않습니다.
예를 들어 2026 접수분에는 2025 계약 18,415건이 포함됩니다. 또한 API가
2023 접수연도 조회에 `INFO-200`을 반환해 포털의 2023 파일을 추가했습니다.
해당 파일에는 계약일 기준으로 2023년 529,877건뿐 아니라 2022년 15,831건과
2024년 105건도 들어 있습니다. 여러 원자료 사이에 동일한 계약 필드 조합이
반복되는 행이 있으므로, 분석용 집계에서는 파일 간 중복을 검토하되 같은 파일
안의 값이 동일한 계약을 무조건 삭제하지 않도록 주의합니다.

```sh
set -a
. ./.env
set +a
python3 scripts/fetch_api.py
```

실행 인자는 필요할 때 명시할 수 있습니다. 재개 전에는 해당 연도의 완성 JSONL이
이미 있는지 확인하고, 부분 실패 시 `.part` 파일을 지우지 않고 동일 명령을 다시
실행하면 처음부터 재수집합니다. 원본 금액 단위는 공식 정의를 확인하기 전까지
변환하지 않습니다.

2023 접수연도는 올바른 API 필터에서도 `INFO-200`을 반환했고, 포털 안내상
OpenAPI는 최근 3년 자료만 제공합니다. 따라서 2023 접수분은 포털의 연도별 파일을
별도로 받아야 합니다. 최종 5개년 분석은 확보한 전체 자료를 `CTRT_DAY` 계약연도로
필터링합니다.

## 출처 간 중복 정리

표준화 CSV의 23개 API 필드가 모두 일치하고 `SOURCE_FILE`이 다른 행만 출처 간
중복 후보로 봅니다. 접수연도가 다른 행은 보존합니다. 거래 고유 ID가 없어 두 행이
실제 같은 계약인지 확정할 수 없으므로, 같은 원본 파일 안의 반복 행은 모두
보존합니다. 출처 간 후보는 한 원본 파일에서 관측된 최대 반복 횟수만 남기고
나머지를 별도 파일에 보존합니다. 보존 원본은 해당 후보를 가장 많이 포함한
파일이며 동률이면 표준화 파일에서 먼저 나타난 파일입니다.

```sh
python3 scripts/deduplicate_data.py
```

기본 입력은 `data/processed/seoul_rent_standardized.csv.gz`이며 새 파일을
덮어쓰지 않습니다. 분석용 결과는
`data/processed/seoul_rent_deduplicated.csv.gz`, 제외한 행은
`data/processed/seoul_rent_overlap_removed.csv.gz`, 출처별 행 수/선택 결과는
`data/processed/seoul_rent_overlap_groups.csv.gz`에 기록합니다. 원본 및 표준화
파일은 변경하지 않습니다. 제외된 행도 출처와 행 번호를 포함해 보존되므로
필요하면 재검토할 수 있습니다. 이 처리는 확정 중복 제거가 아니라, 출처 중복
가능성이 높은 행을 재현 가능하게 한 번만 분석에 반영하는 규칙입니다.
2026년 10월 14일 실행 결과, 입력 4,281,097행 중 6,213개 겹침 그룹에서
6,213행을 제외했고 4,274,884행을 분석용 파일에 남겼습니다. 같은 원본 파일
안에서 동일한 필드 조합을 가진 행은 별도 계약일 가능성을 배제할 수 없어
제거하지 않았습니다.

## 자치구·건물용도별 전세 ㎡당 보증금 분석

현재 구현된 기본 분석은 중복제거 자료를 입력으로 사용하고, 아래 순서로
HTML 보고서를 생성합니다.

1. `data/processed/seoul_rent_deduplicated.csv.gz`에서 전세·월세 계약을 선택합니다.
2. 계약일이 2021~2025년이고 면적이 양수인 유효 행을 사용합니다. 월세는 월세액이
   유효한 행만 포함합니다.
3. 계약별 전세환산 보증금 `GRFE + (RTFE × 12 ÷ 0.05)`를 계산한 다음
   `RENT_AREA(㎡)`로 나눕니다. 전세 계약의 월세액은 0으로 계산합니다.
4. 자치구·건물용도·월별 거래 건수, 최솟값, 중앙값, 최댓값을 집계합니다.
5. 자치구·건물용도·연도별 거래 건수와 ㎡당 보증금 최솟값·중앙값·최댓값을 집계합니다.
6. 월별 그래프는 연도 눈금과 마우스오버 안내선을 제공하고, 중앙값·최솟값~최댓값·
   거래 건수를 별도 정보 상자에 표시합니다. 자치구 중앙값 막대그래프는 연도와
   건물용도를 선택하며, 막대에 마우스를 올리면 최솟값·최댓값을 보여줍니다.
   세 번째 그래프는 자치구별 연도별 중앙값을 표시하며, 모든 자치구에서 같은 연도는
   같은 색으로 구분하고 이름순으로 정렬합니다.
7. 각 그래프 아래에 단위와 읽는 법을 설명하는 카드를 표시합니다.
8. 같은 분석 모집단에서 `MNO`, `SNO` 결측률과 결측 조합을 요약합니다.

```sh
python3 scripts/analyze_rent.py
```

기본 출력은 `reports/seoul_jeonse_per_sqm.html`과 월별 집계 파일
